# Chapter 7: Building Production Applications

## Project Structure

A well-organized Ovie project:

```
my-app/
├── ovie.toml          # Project manifest
├── ovie.lock          # Dependency lock file
├── src/
│   ├── main.ov        # Entry point
│   ├── config.ov      # Configuration
│   ├── handlers/      # Request/event handlers
│   │   └── mod.ov
│   └── utils/         # Shared utilities
│       └── mod.ov
├── tests/
│   └── integration.ov
└── docs/
    └── api/           # Generated by ovie doc
```

## Configuration Management

Use environment variables for configuration:

```ovie
use std::env::{get_var}

struct AppConfig {
    port: Number,
    db_path: String,
    log_level: String,
}

fn load_config() -> AppConfig {
    return AppConfig {
        port: string_to_number(get_var("PORT")),
        db_path: get_var("DB_PATH"),
        log_level: get_var("LOG_LEVEL"),
    }
}
```

For local development, use a `.env` file pattern:

```ovie
use std::fs::{read_file, file_exists}

fn load_env_file(path: String) {
    if !file_exists(path) { return; }
    mut content = read_file(path)
    mut lines = string_split_lines(content)
    mut i = 0
    while i < array_length(lines) {
        mut line = string_trim(array_get(lines, i))
        if string_length(line) > 0 && !string_starts_with(line, "#") {
            mut eq = string_find(line, "=")
            if eq > 0 {
                mut key = string_substring(line, 0, eq)
                mut val = string_substring(line, eq + 1, string_length(line))
                set_env_var(key, val)
            }
        }
        i = i + 1
    }
}
```

## Logging and Monitoring

Use structured logging:

```ovie
use std::log::{info, warn, error}

fn process_request(request_id: String, data: String) {
    info("Processing request: " + request_id)

    mut result = handle(data)
    if result.is_err() {
        error("Request failed: " + request_id + " — " + result.unwrap_err())
        return
    }

    info("Request complete: " + request_id)
}
```

## Error Handling Strategies

Always use `Result` for operations that can fail:

```ovie
use std::core::{Result}
use std::fs::{read_file}
use std::log::{error}

fn load_data(path: String) -> Result {
    if !file_exists(path) {
        return Result.Err("File not found: " + path)
    }
    mut content = read_file(path)
    return Result.Ok(content)
}

fn main() {
    mut r = load_data("config.json")
    if r.is_err() {
        error(r.unwrap_err())
        return
    }
    mut data = r.unwrap()
    // process data...
}
```

## Security Best Practices

- Never hardcode secrets — use environment variables
- Validate all external input before processing
- Use `unsafe` blocks only when absolutely necessary, with a comment explaining why
- Keep dependencies minimal and pinned in `ovie.lock`
- Run `oviec analyze` before every release

```ovie
fn validate_input(input: String) -> Result {
    if string_length(input) == 0 {
        return Result.Err("Input cannot be empty")
    }
    if string_length(input) > 1000 {
        return Result.Err("Input too long (max 1000 chars)")
    }
    // Check for path traversal
    if string_contains(input, "..") {
        return Result.Err("Invalid characters in input")
    }
    return Result.Ok(input)
}
```

## Performance Considerations

- Use the module cache — don't clear it unnecessarily
- Prefer `Vec` over raw arrays for dynamic collections
- Use `std::math` functions — they're optimized
- Profile before optimizing (see Chapter 9)

## Deployment Preparation

Build for production:

```bash
oviec build --backend wasm src/main.ov
```

Check the build:

```bash
oviec --self-check
oviec analyze src/main.ov
ovie test
ovie doc check
```

Package for distribution:

```bash
oviec build-package
```

This creates platform-specific packages in `target/dist/`.
